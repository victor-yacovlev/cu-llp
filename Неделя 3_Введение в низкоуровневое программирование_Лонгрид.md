## Внутреннее представление целых типов данных

Любое целое число в памяти компьютера хранится в виде фиксированного количества бит &mdash; ровно
`sizeof(тип) * 8` бит для типа данного размера. Для беззнаковых типов представление прямое: число
записывается непосредственно в двоичной системе счисления. Например, число 5 в 32-битном представлении
&mdash; это `00000000 00000000 00000000 00000101`.

Для знаковых типов вопрос сложнее: нужно как-то закодировать ещё и знак числа. Исторически существовало
три способа представления отрицательных чисел: *прямой код* (знаковый бит отдельно от абсолютного значения),
*обратный код* (инвертирование всех бит положительного числа) и *дополнительный код* (two's complement).
На всех современных процессорах (x86, ARM, RiscV) используется именно дополнительный код, и начиная со
стандарта C23 он закреплён как единственный разрешённый способ представления знаковых целых чисел.

Дополнительный код отрицательного числа `-x` получается по правилу: инвертировать все биты положительного
числа `x` (заменить каждый 0 на 1 и каждую 1 на 0), а затем прибавить к результату 1.

Посмотрим на битовое представление нескольких чисел с помощью небольшой вспомогательной функции:

```c
#include <stdio.h>
#include <stdint.h>

void print_bits(int32_t value)
{
    uint32_t bits = (uint32_t) value;   // работаем с битовым представлением как с беззнаковым числом
    for (int i = 31; i >= 0; --i) {
        putchar((bits >> i) & 1u ? '1' : '0');
        if (i % 8 == 0 && i != 0) putchar(' ');
    }
    putchar('\n');
}

int main(void)
{
    print_bits(5);
    print_bits(-5);
    print_bits(0);
    print_bits(-1);
    return 0;
}
```

Результат работы программы:

```
00000000 00000000 00000000 00000101
11111111 11111111 11111111 11111011
00000000 00000000 00000000 00000000
11111111 11111111 11111111 11111111
```

Проверим правило дополнительного кода на примере -5: биты числа 5 &mdash; это `...00000101`; инвертируем их
и получаем `...11111010`; прибавляем 1 и получаем `...11111011` &mdash; именно это мы и видим в выводе
программы для `-5`. Обратите внимание на два частных случая: representation числа 0 состоит целиком из нулей
(и это единственное представление нуля &mdash; в отличие от обратного кода, в дополнительном коде нет
отдельного "минус нуля"), а representation числа -1 состоит целиком из единиц.

Обратите внимание, что в функции `print_bits` мы явно преобразуем значение параметра типа `int32_t` к типу
`uint32_t` перед побитовыми операциями. Это сделано намеренно: сдвиг отрицательного знакового числа вправо
в языке C имеет implementation-defined (то есть определённое конкретной платформой, но не
гарантированное стандартом) поведение, тогда как сдвиг беззнакового числа всегда однозначно определён
стандартом. Поэтому, работая непосредственно с битами числа, правильнее заранее привести его к
соответствующему беззнаковому типу.

## Работа с внутренним представлением целочисленных типов данных

Чтобы посмотреть на битовое представление числа на практике, есть два основных инструмента: вывод числа в
шестнадцатеричном виде и побайтовое чтение представления переменной из памяти.

### Шестнадцатеричный вывод отрицательных чисел

Спецификатор `%x` функции `printf` рассчитан на аргумент типа `unsigned int` и всегда выводит именно
битовое представление числа, а не его знаковое десятичное значение. Поэтому, чтобы увидеть шестнадцатеричное
представление отрицательного числа, его нужно предварительно явно привести к соответствующему беззнаковому
типу.

```c
#include <stdio.h>

int main(void)
{
    int x = -5;
    printf("%d\n", x);
    printf("%x\n", (unsigned) x);
    printf("%#010x\n", (unsigned) x);
    return 0;
}
```

Результат работы программы:

```
-5
fffffffb
0xfffffffb
```

Формат `%#010x` выводит число с префиксом `0x` (флаг `#`) и дополняет его нулями слева до общей ширины поля
в 10 символов (флаг `0` и ширина `10`), что удобно для чтения: сразу видно, что перед нами 32-битное число
целиком из шестнадцатеричных цифр `f`.

### Побайтовое чтение представления переменной

Модель памяти языка C позволяет получить указатель на любой объект, привести его к типу `unsigned char *`
и с его помощью прочитать представление объекта побайтово &mdash; такое преобразование указателя всегда
корректно, в отличие от преобразования к указателю на произвольный несовместимый тип.

```c
#include <stdio.h>
#include <stdint.h>

int main(void)
{
    int32_t x = 0x01020304;
    unsigned char *bytes = (unsigned char *) &x;

    for (size_t i = 0; i < sizeof(x); ++i) {
        printf("byte[%zu] = 0x%02x\n", i, bytes[i]);
    }
    return 0;
}
```

Результат работы программы:

```
byte[0] = 0x04
byte[1] = 0x03
byte[2] = 0x02
byte[3] = 0x01
```

Число `0x01020304` в памяти хранится байтами `04 03 02 01`, то есть младший байт числа (`0x04`) находится
по наименьшему адресу &mdash; это порядок байт *little-endian*, который используется на процессорах Intel
x86 и, в подавляющем большинстве конфигураций, на ARM. Существует и обратный порядок, *big-endian*, при
котором старший байт числа хранится по наименьшему адресу, но на распространённых сегодня платформах он
почти не встречается.

## Битовые сдвиги и логические операции

Кроме обычных арифметических операторов, в языке C есть операторы, работающие непосредственно с отдельными
битами целого числа: побитовое И `&`, побитовое ИЛИ `|`, побитовое исключающее ИЛИ `^`, побитовое отрицание
`~`, сдвиг влево `<<` и сдвиг вправо `>>`.

Типичное применение битовых операций &mdash; хранение набора независимых булевских флагов в одной
целочисленной переменной, где каждый бит отвечает за свой флаг.

```c
#include <stdio.h>

int main(void)
{
    unsigned int flags = 0;
    unsigned int FLAG_READ  = 1u << 0;
    unsigned int FLAG_WRITE = 1u << 1;
    unsigned int FLAG_EXEC  = 1u << 2;

    flags |= FLAG_READ | FLAG_WRITE;      // устанавливаем флаги
    printf("flags after set: %u\n", flags);

    printf("has read: %d\n", (flags & FLAG_READ) != 0);
    printf("has exec: %d\n", (flags & FLAG_EXEC) != 0);

    flags &= ~FLAG_WRITE;                 // сбрасываем флаг WRITE
    printf("flags after clear write: %u\n", flags);

    flags ^= FLAG_EXEC;                   // переключаем флаг EXEC
    printf("flags after toggle exec: %u\n", flags);
    return 0;
}
```

Результат работы программы:

```
flags after set: 3
has read: 1
has exec: 0
flags after clear write: 1
flags after toggle exec: 5
```

Здесь `1u << 0`, `1u << 1`, `1u << 2` задают три флага, у каждого из которых установлен ровно один бит на
своей позиции. Оператор `|=` устанавливает биты (объединяет набор флагов с новыми), оператор `&` вместе с
проверкой на неравенство нулю проверяет, установлен ли конкретный бит, конструкция `&= ~FLAG` сбрасывает
конкретный бит (побитовое отрицание `~FLAG` даёт число, где установлены все биты, кроме бита самого флага),
а оператор `^=` переключает бит &mdash; если он был установлен, сбрасывает его, и наоборот.

### Арифметический и логический сдвиг вправо

Сдвиг влево `<<` всегда заполняет освобождающиеся справа биты нулями. Со сдвигом вправо `>>` ситуация
сложнее: для беззнаковых чисел он всегда выполняется как *логический сдвиг*, заполняя освобождающиеся
слева биты нулями, а для знаковых чисел, если исходное число отрицательное, компилятор, как правило,
выполняет *арифметический сдвиг*, заполняя освобождающиеся биты значением знакового бита (то есть
единицами), чтобы сохранить знак числа. Такое поведение для знаковых чисел не гарантировано стандартом
языка, но фактически реализовано на всех распространённых сегодня компиляторах и платформах.

```c
#include <stdio.h>

int main(void)
{
    int neg = -8;
    unsigned int u = (unsigned int) neg;

    printf("%d >> 1 = %d\n", neg, neg >> 1);
    printf("%u >> 1 = %u\n", u, u >> 1);
    printf("%d << 2 = %d\n", 3, 3 << 2);
    return 0;
}
```

Результат работы программы:

```
-8 >> 1 = -4
4294967288 >> 1 = 2147483644
3 << 2 = 12
```

Число `-8` после арифметического сдвига вправо на 1 бит стало `-4` &mdash; знак сохранился, как при
целочисленном делении на 2. То же самое битовое представление, но интерпретированное как беззнаковое число
`4294967288`, после логического сдвига вправо на 1 бит превратилось в совсем другое число `2147483644`,
потому что освободившийся старший бит заполнился нулём, а не единицей.

## Внутреннее представление вещественного числа

### Три составляющих части

Вещественные числа одинарной точности (`float`) хранятся в памяти согласно стандарту IEEE754 в виде трёх
частей общей длиной 32 бита:

| Часть | Количество бит | Назначение |
| - | - | - |
| Знак (sign) | 1 бит | 0 &mdash; положительное число, 1 &mdash; отрицательное |
| Экспонента (exponent) | 8 бит | Степень двойки, смещённая (biased) на константу 127 |
| Мантисса (mantissa) | 23 бита | Значащие цифры дробной части числа |

Для сравнения, вещественные числа двойной точности (`double`) устроены точно по такому же принципу, но с
бóльшим количеством бит, отведённых под экспоненту и мантиссу, что даёт больший диапазон и точность:

| Тип | Знак | Экспонента | Мантисса | Смещение экспоненты |
| - | - | - | - | - |
| `float` | 1 бит | 8 бит | 23 бита | 127 |
| `double` | 1 бит | 11 бит | 52 бита | 1023 |

Значение нормализованного числа вычисляется по формуле `(-1)^sign * 1.mantissa * 2^(exponent - смещение)`,
где `1.mantissa` означает, что перед битами мантиссы неявно (то есть не хранясь в памяти явно) подразумевается
ведущая единица &mdash; это возможно, потому что любое ненулевое число в нормализованной двоичной форме
записи всегда начинается именно с 1, и хранить этот бит в памяти было бы избыточно; так экономится один бит
точности.

### Почему экспонента хранится со смещением

Экспонента могла бы храниться и в дополнительном коде, как обычное знаковое число, но вместо этого выбрано
представление со смещением (`exponent - 127` вместо самой экспоненты). У этого решения есть практическое
удобство: если сравнивать битовые представления двух *положительных* вещественных чисел просто как обычные
целые беззнаковые числа &mdash; байт за байтом, начиная со старшего &mdash; результат сравнения совпадёт с
результатом сравнения самих вещественных чисел. Такое было бы невозможно, если бы экспонента с отрицательным
значением хранилась в дополнительном коде, потому что тогда у отрицательных степеней двойки старший бит
экспоненты был бы установлен в 1, и такое число ошибочно выглядело бы "больше" чисел с положительной
степенью двойки при побитовом сравнении.

### Специальные значения

Не все комбинации бит экспоненты кодируют обычные нормализованные числа. Два значения экспоненты
зарезервированы под особые случаи.

| Экспонента (смещённая) | Мантисса | Что представляет |
| - | - | - |
| `0` | `0` | Ноль (знак определяет `+0` или `-0`) |
| `0` | не `0` | Денормализованное (субнормальное) число |
| `1` ... `254` | любая | Обычное нормализованное число |
| `255` | `0` | Бесконечность (знак определяет `+inf` или `-inf`) |
| `255` | не `0` | NaN (Not a Number &mdash; результат некорректной операции) |

Когда смещённая экспонента равна 0, ведущая единица перед мантиссой уже не подразумевается неявно: такие
числа называются *денормализованными* (denormalized) или *субнормальными* (subnormal) и вычисляются по
слегка изменённой формуле `(-1)^sign * 0.mantissa * 2^(1 - 127)`, то есть с ведущим нулём вместо ведущей
единицы. Субнормальные числа позволяют представлять величины меньше минимального нормализованного числа
(`~1.18 * 10^-38` для `float`), постепенно теряя значащие биты мантиссы по мере приближения к нулю &mdash;
такой механизм называется *постепенным исчезновением порядка* (gradual underflow) и позволяет избежать
резкого скачка от наименьшего представимого положительного числа сразу к нулю.

Значение `+0.0` и `-0.0` &mdash; это два разных битовых представления, которые тем не менее считаются
равными при сравнении операторами `==` и `!=`; знаковый бит нуля влияет, например, на результат деления
на этот ноль (`1.0 / +0.0` даёт `+inf`, а `1.0 / -0.0` даёт `-inf`).

Значение `NaN` возникает как результат операций, не имеющих определённого числового результата, например
`0.0 / 0.0` или взятие квадратного корня из отрицательного числа. Стандарт не фиксирует единственное
битовое представление `NaN` &mdash; допустима любая мантисса, кроме нулевой, при экспоненте `255`, поэтому
разные операции и разные платформы могут порождать `NaN` с разными битами мантиссы и разным знаковым битом;
знак у `NaN`, в отличие от обычных чисел, не несёт смысловой нагрузки.

Посмотрим на битовое представление перечисленных особых случаев на практике:

```c
#include <stdio.h>
#include <stdint.h>

void show(const char *label, float f)
{
    union { float f; uint32_t u; } v;
    v.f = f;
    uint32_t sign = (v.u >> 31) & 0x1u;
    uint32_t exp_biased = (v.u >> 23) & 0xFFu;
    uint32_t mantissa = v.u & 0x7FFFFFu;
    printf("%-16s value=%-14g raw=0x%08x sign=%u exp=%3u mantissa=0x%06x\n",
           label, (double) f, v.u, sign, exp_biased, mantissa);
}

int main(void)
{
    volatile float zero = 0.0f;
    volatile float one = 1.0f;
    volatile float minus_one = -1.0f;

    show("+0.0", zero);
    show("-0.0", -zero);
    show("1.0", one);
    show("smallest normal", 1.17549435e-38f);
    show("subnormal", 1.0e-40f);
    show("+infinity", one / zero);
    show("-infinity", minus_one / zero);
    show("NaN", zero / zero);
    return 0;
}
```

Результат работы программы:

```
+0.0             value=0              raw=0x00000000 sign=0 exp=  0 mantissa=0x000000
-0.0             value=-0             raw=0x80000000 sign=1 exp=  0 mantissa=0x000000
1.0              value=1              raw=0x3f800000 sign=0 exp=127 mantissa=0x000000
smallest normal  value=1.17549e-38    raw=0x00800000 sign=0 exp=  1 mantissa=0x000000
subnormal        value=9.99995e-41    raw=0x000116c2 sign=0 exp=  0 mantissa=0x0116c2
+infinity        value=inf            raw=0x7f800000 sign=0 exp=255 mantissa=0x000000
-infinity        value=-inf           raw=0xff800000 sign=1 exp=255 mantissa=0x000000
NaN              value=-nan           raw=0xffc00000 sign=1 exp=255 mantissa=0x400000
```

Переменные объявлены с модификатором `volatile`, чтобы компилятор не вычислил операции деления во время
компиляции, а действительно выполнил их во время работы программы на реальном оборудовании. Обратите
внимание на строку `smallest normal`: экспонента здесь равна 1 (минимально возможное значение для
нормализованного числа), а на следующей строке, `subnormal`, для ещё меньшего по модулю числа экспонента
уже равна 0, а мантисса ненулевая &mdash; это и есть денормализованное представление. Также обратите
внимание, что `NaN`, полученный из `0.0 / 0.0` на данной платформе, оказался со знаковым битом, равным 1
(отображается как `-nan`), хотя знак `NaN`, как было сказано выше, не несёт смыслового значения.

### Разбор конкретного числа

Посмотрим на разбор обычного, нормализованного числа `13.375` на составляющие части с помощью объединения
(`union`), позволяющего интерпретировать одну и ту же область памяти то как значение типа `float`, то как
значение типа `uint32_t`:

```c
#include <stdio.h>
#include <stdint.h>

int main(void)
{
    union { float f; uint32_t u; } v;
    v.f = 13.375f;

    uint32_t sign = (v.u >> 31) & 0x1u;
    uint32_t exp_biased = (v.u >> 23) & 0xFFu;
    uint32_t mantissa = v.u & 0x7FFFFFu;

    int exp = (int) exp_biased - 127;

    printf("float = %.6f\n", v.f);
    printf("raw bits = 0x%08x\n", v.u);
    printf("sign = %u\n", sign);
    printf("biased exponent = %u, real exponent = %d\n", exp_biased, exp);
    printf("mantissa bits = 0x%06x\n", mantissa);
    return 0;
}
```

Результат работы программы:

```
float = 13.375000
raw bits = 0x41560000
sign = 0
biased exponent = 130, real exponent = 3
mantissa bits = 0x560000
```

Знак равен 0, значит число положительное. Смещённая экспонента равна 130, а реальная экспонента &mdash;
`130 - 127 = 3`, то есть множитель `2^3 = 8`. Действительно, `13.375 = 1.671875 * 8`, а мантисса `0x560000`
&mdash; это как раз двоичная запись дробной части `0.671875` в 23-битном представлении.

## Разбор примера: мантисса и целая часть вещественного числа через сдвиг и через union

Рассмотрим два практически эквивалентных способа получить мантиссу и целую часть вещественного числа из
его битового представления: явными сдвигами и масками поверх `union { float; uint32_t }`, и через `union`
со структурой битовых полей.

### Способ первый: сдвиги и маски

Мы уже получили значения `exp_biased` и `mantissa` в примере выше с помощью операторов сдвига `>>` и
побитового И `&` с масками. Восстановим по ним ещё и целую часть исходного числа.

```c
#include <stdio.h>
#include <stdint.h>

int main(void)
{
    union { float f; uint32_t u; } v;
    v.f = 13.375f;

    uint32_t exp_biased = (v.u >> 23) & 0xFFu;
    uint32_t mantissa    = v.u & 0x7FFFFFu;
    int exp = (int) exp_biased - 127;

    uint32_t full_mantissa = (1u << 23) | mantissa;   // добавляем неявную единицу
    uint32_t int_part = full_mantissa >> (23 - exp);  // сдвигаем так, чтобы точка оказалась в конце

    printf("value = %.6f\n", v.f);
    printf("integer part = %u\n", int_part);
    return 0;
}
```

Результат работы программы:

```
value = 13.375000
integer part = 13
```

Идея этого способа такая: 23-битная мантисса вместе с неявной единицей образует 24-битное целое число
`1.mantissa`, домноженное на `2^23` (то есть мантисса записана как если бы точка стояла сразу после этих
24 бит). Чтобы получить именно целую часть исходного числа `1.mantissa * 2^exp`, нужно сдвинуть эти 24 бита
вправо на `23 - exp` позиций, тем самым переместив точку туда, где она должна быть после умножения на
`2^exp`. Этот приём работает, только пока `0 <= exp <= 23`, то есть пока у числа действительно есть и целая,
и дробная часть, представимая в пределах мантиссы; для чисел с экспонентой за пределами этого диапазона
потребовалась бы дополнительная обработка граничных случаев.

### Способ второй: union со структурой битовых полей

Тот же самый результат можно получить нагляднее, если объявить объединение вещественного числа со
структурой, поля которой явно описывают знак, экспоненту и мантиссу с помощью *битовых полей*
(bit fields) &mdash; синтаксиса, позволяющего указать, сколько именно бит отводится под каждое поле
структуры.

```c
#include <stdio.h>

typedef union {
    float f;
    struct {
        unsigned int mantissa : 23;
        unsigned int exponent : 8;
        unsigned int sign     : 1;
    } bits;
} FloatBits;

int main(void)
{
    FloatBits v;
    v.f = 13.375f;

    printf("sign = %u\n", v.bits.sign);
    printf("biased exponent = %u\n", v.bits.exponent);
    printf("mantissa bits = 0x%06x\n", v.bits.mantissa);
    return 0;
}
```

Результат работы программы:

```
sign = 0
biased exponent = 130
mantissa bits = 0x560000
```

Результат в точности совпадает с тем, что мы получили ранее сдвигами и масками. Однако у этого способа
есть важная оговорка: стандарт языка C не фиксирует, в каком порядке компилятор располагает битовые поля
внутри слова памяти (то есть, начинается ли перечисление полей структуры с младших бит или со старших)
&mdash; это implementation-defined поведение, зависящее от компилятора и платформы. Приведённый код даёт
верный результат на распространённых сегодня компиляторах (GCC, Clang) на платформах x86 и ARM, но не
гарантированно даст такой же результат на других компиляторах, поэтому для действительно переносимого кода
предпочтительнее явный способ со сдвигами и масками, порядок действий в котором мы полностью контролируем
сами.
